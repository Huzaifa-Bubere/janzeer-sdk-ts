# Conformance

Janzeer's signing scheme is custom (see [wallet-and-keys](wallet-and-keys.md)); a client that deviates by one
byte produces transactions every node rejects. Two artefacts keep every official SDK — and any third-party
client — in line:

1. **Vectors** — `sdk_conformance/vectors/wallet-parity-vectors.json`, generated by the node's own crypto:
   mnemonic → seed → key → address, a raw-key address, and for each transaction type the exact preimage bytes,
   hash and signature. Plus an EIP-55 table and a `toScaledLong` table. This SDK vendors them under
   `test/vectors/` and `npm test` reproduces every entry; `npm run check:vectors` verifies the copy against the
   kit's `SHA256SUMS`.
2. **The e2e flow** — `sdk_conformance/e2e/SPEC.md`, 14 steps against a real network: version gate, account,
   subscribe, build/sign, submit over REST, idempotent resubmit over RPC, finality on another node, exact
   balance arithmetic, the WebSocket notification, and three negative cases (nonce gap, forged signature, bad
   address). `npm run e2e` runs it (`JANZEER_NODE_URL` etc. from `node-up.sh --env`).

## Writing your own client?

Reproduce the vectors first, in this order: `scaled` → `hd` (seed, key, address) → `rawKey` → `transferTx`
preimage → hash → signature (RFC-6979, low-S, DER, Base64, **over the raw digest** — no re-hashing) → the other
types. Then run the SPEC flow. The developer guide's chapter *Build on Janzeer* explains each byte layout.
